# NeuroForge 架构设计文档

> 非 Transformer 自学习编程智能体 | v0.1 Draft
> 2026-10-17

---

## 1. 项目定位

NeuroForge 是一个**能阅读、修改并验证自身源码**的 AI 智能体，其核心学习引擎**不依赖 Transformer/Attention 机制**。它同时承担两个使命：

1. **实用层**：在受限 DSL 内自主优化自身算法模块
2. **研究层**：探索 "SSM + 神经符号" 混合范式能否替代 LLM 完成代码理解与生成

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| **可验证优先** | 每次自修改必须通过类型检查 + 沙箱测试，否则回滚 |
| **轻量可运行** | 总参数 < 50M，CPU 实时推理，单开发者可维护 |
| **渐进式复杂度** | Phase 0-1 即为最小可用版本，SSM 可后期接入 |
| **安全内核不可变** | 验证基础设施本身不在自修改范围内 |

## 2. 候选范式评估

### 2.1 三种非 Transformer 路线对比

| 维度 | Mamba / SSM | Liquid Neural Net | DreamCoder 式神经符号 |
|------|-------------|-------------------|----------------------|
| **序列建模** | ★★★★★ O(n) 线性扫描，长程依赖优秀 | ★★★☆ 连续时间 ODE，适合控制信号 | ★★☆ 枚举搜索，非序列模型 |
| **代码生成适配** | ★★★☆ 可预测 token，但无结构保证 | ★★☆ 连续动态 vs 离散符号天然不匹配 | ★★★★★ 输出即程序，天然可执行 |
| **CPU 友好度** | ★★★★ 递归状态更新，无需并行注意力 | ★★★ ODE 求解器有开销 | ★★★★★ 搜索+小网络，极轻量 |
| **可解释性** | ★★☆ 隐状态难解读 | ★★☆ ODE 轨迹可视化但语义不明 | ★★★★★ 程序本身就是解释 |
| **自修改支持** | ★★☆ 权重不可直接编辑为代码 | ★☆☆ 同上 | ★★★★★ 函数库即知识库，增删改查即修改 |
| **生态成熟度** | ★★★ mamba-ssm, causal-conv1d | ★★ torchdiffeq, cfode | ★★ dreamcoder, fleure |
| **训练数据需求** | ★★★★ 需要大量代码语料 | ★★★ 需要时序数据 | ★★☆ 少量示例即可启动 |

### 2.2 选型结论：SSM + 神经符号混合

单一范式无法同时满足 "理解代码" 和 "生成正确代码" 两个目标。混合架构让两者各司其职：

```
┌─────────────────────────────────────────────────┐
│              NeuroForge 混合架构                  │
│                                                   │
│  ┌──────────────┐    ┌──────────────────────┐    │
│  │  System 1     │    │  System 2             │    │
│  │  Mamba SSM    │◄──►│  符号引擎             │    │
│  │  (直觉引擎)   │    │  (理性引擎)           │    │
│  │               │    │                       │    │
│  │ • 模式识别    │    │ • HM 类型推断         │    │
│  │ • 编辑位置预测│    │ • 类型引导程序合成    │    │
│  │ • 自然语言理解│    │ • 等价性验证          │    │
│  │ • ~30M params │    │ • 契约检查            │    │
│  └──────────────┘    └──────────────────────┘    │
│         ▲                     ▲                   │
│         │                     │                   │
│  ┌──────┴─────────────────────┴──────────────┐   │
│  │         可编辑函数知识库 (DSL)              │   │
│  │  • AST 存储  • 类型签名  • 测试用例        │   │
│  │  • 版本历史  • 依赖图    • 性能指标        │   │
│  └───────────────────────────────────────────┘   │
│                        ▲                          │
│  ┌─────────────────────┴──────────────────────┐  │
│  │         安全内核 (不可修改)                   │  │
│  │  • 类型检查器  • 沙箱执行器  • Git 回滚     │  │
│  │  • 资源限制器  • 宪法约束                    │  │
│  └────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**为什么不是纯 SSM？** SSM 可以预测下一个 token，但无法保证生成的代码类型正确、终止、不越界。符号层提供形式化保障。

**为什么不是纯符号？** 纯枚举搜索在稍大的程序空间就组合爆炸。SSM 提供 "有根据的猜测"，将搜索空间缩小数个数量级。

## 3. 核心模块详解

### 3.1 DSL 设计：ForgeLang

自修改的目标语言不是通用 Python，而是一个精心设计的受限 DSL：

```python
# ForgeLang 示例：一个排序函数
@forge_fn(sig="[Int] -> [Int]")
def bubble_sort(xs: List[Int]) -> List[Int]:
    n = len(xs)
    for i in range(n):
        for j in range(n - i - 1):
            if xs[j] > xs[j + 1]:
                xs = swap(xs, j, j + 1)
    return xs

# 类型签名由 HM Algorithm W 自动推断或手动标注
# 所有函数必须是纯函数（无副作用）
# 递归必须有结构性递减参数（保证终止）
```

**DSL 约束清单：**

| 约束 | 目的 |
|------|------|
| 纯函数 only | 消除副作用使等价验证可行 |
| 强类型 + HM 推断 | 编译期捕获类型错误 |
| 结构化递归 | 保证所有程序终止 |
| 无 eval/exec | 防止代码注入 |
| 资源上限注解 | 每个函数标注最大步数/内存 |
| 不可导入外部模块 | 封闭世界假设 |

### 3.2 符号引擎 (System 2)

#### 3.2.1 类型系统：Hindley-Milner Algorithm W

```
输入: ForgeLang AST
输出: 类型签名 或 类型错误

流程:
1. 解析 → AST
2. 约束生成 (遍历 AST，收集类型等式)
3. 统一求解 (Robinson 统一算法)
4. 泛化 (let-polymorphism)
5. 返回最一般类型
```

这是整个安全体系的基石——任何自修改后的代码必须先过类型检查。

#### 3.2.2 程序合成器

采用**类型引导的枚举搜索** (Type-Directed Enumeration)：

```
给定: 目标类型 T, 可用原语集合 P, 深度上限 d
输出: 所有类型为 T 且深度 ≤ d 的程序

算法:
1. 按类型对 P 分组
2. 自底向上构造: depth=1 的程序 = P 中类型为 T 的原语
3. depth=k 的程序 = 将 depth<k 的子程序用 P 中的构造器组合
4. 剪枝: 类型不匹配的分支立即丢弃
5. SSM 引导: 用 SSM 输出的概率分布重排搜索顺序
```

关键创新：**SSM 不做最终决策，只做搜索排序**。即使 SSM 给出错误建议，符号搜索仍能找到正确答案（只是慢一些）。这保证了系统的可靠性下限。

#### 3.2.3 等价性验证

自修改声称 "改进" 时，必须证明新旧版本行为等价（或在指定测试集上等价）：

- **符号等价**: 对小型函数，使用基于重写规则的等价证明
- **测试等价**: 对大型函数，使用属性测试 (property-based testing) + 穷举小输入
- **性能比较**: 基准测试确保 "改进" 确实更快/更省内存

### 3.3 SSM 直觉引擎 (System 1)

#### 3.3.1 架构：MambaCodeEncoder

```
输入表示:
  - 代码 token 序列 (ForgeLang tokenizer)
  - 类型嵌入 (从符号引擎注入)
  - AST 结构编码 (Tree Positional Encoding)

核心层:
  - 4-layer Mamba block (d_model=256, d_state=16)
  - 每层后接 Type-Aware Gating (用类型信息调制 SSM 参数)
  - 总参数 ~30M

输出头:
  - Edit Location Head: 预测哪些函数需要修改 (序列标注)
  - Edit Type Head: 分类修改类型 (优化/重构/修复/扩展)
  - Sketch Head: 生成修改草稿 (token 级预测)
```

#### 3.3.2 训练策略

由于目标是研究而非刷榜，采用小规模高质量数据：

| 数据集 | 规模 | 用途 |
|--------|------|------|
| 人工构造的 ForgeLang 函数对 | ~5K 对 | 学习基本变换模式 |
| Rosetta Code 翻译到 ForgeLang | ~2K | 算法模式库 |
| 自修改日志 (bootstrapping) | 持续增长 | 在线学习 |
| 合成错误→修复对 | ~10K | 调试能力 |

训练目标不是 next-token prediction，而是 **structured edit prediction**：给定当前代码 + 任务描述，预测编辑操作的 AST diff。

### 3.4 自修改流水线

七阶段闭环，每次修改都走完整个流程：

```
Stage 1: INTENT     ← 用户指令 / 自我诊断触发
    ↓
Stage 2: LOCATE     ← SSM 定位相关函数 + 符号引擎确认依赖
    ↓
Stage 3: PROPOSE    ← SSM 生成修改草稿 OR 符号合成器生成候选
    ↓
Stage 4: VERIFY-S   ← 类型检查 + 契约验证 (静态)
    ↓                 ✗ → 回到 Stage 3 (最多 3 次)
Stage 5: VERIFY-D   ← 沙箱执行 + 测试 + 性能基准 (动态)
    ↓                 ✗ → 回到 Stage 3 (最多 3 次)
Stage 6: COMMIT     ← Git commit + 更新知识库索引
    ↓
Stage 7: REFLECT    ← 记录本次修改的动机/结果/教训 → 反馈到训练数据
```

### 3.5 安全体系：四层纵深防御

```
Layer 0: 宪法 (Constitution)
  ├── 硬编码规则，不在 DSL 内，不可被任何机制修改
  ├── 定义: 什么是合法修改、资源上限、禁止操作
  └── 实现: Python 原生代码 + 配置常量

Layer 1: 语法+类型 (Static)
  ├── ForgeLang parser 拒绝非法语法
  ├── HM 类型检查拒绝类型错误
  └── 终止性检查拒绝非结构化递归

Layer 2: 沙箱 (Runtime)
  ├── seccomp/nsjail 隔离进程
  ├── CPU 时间上限 (默认 5s)
  ├── 内存上限 (默认 256MB)
  ├── 无文件系统/网络访问
  └── 无 import/os/subprocess

Layer 3: 版本控制 (Recovery)
  ├── 每次修改前自动 git tag
  ├── 验证失败自动 git revert
  ├── 保留完整修改历史 + 元数据
  └── 支持手动审查和回退
```

## 4. 技术栈

| 组件 | 选型 | 理由 |
|------|------|------|
| 语言 | Python 3.11+ | 生态、原型速度、符号计算库丰富 |
| SSM 框架 | mamba-ssm + PyTorch 2.x | 官方实现，CPU fallback 可用 |
| 符号引擎 | 自研 (基于 unification + e-graph) | 现有库不完全匹配 ForgeLang 需求 |
| 类型推断 | 自研 HM Algorithm W | 教学级实现，~500 行，完全可控 |
| 沙箱 | nsjail (Linux) / RestrictedPython (fallback) | 进程级隔离最安全 |
| 版本控制 | gitpython | 编程接口完善 |
| 测试 | hypothesis (属性测试) + pytest | 自动生成边界用例 |
| 序列化 | msgpack (AST) + JSON (配置) | AST 高频读写需二进制格式 |

## 6. 与 LLM+Transformer 的对比

| 维度 | NeuroForge | LLM+Transformer |
|------|-----------|-----------------|
| 代码正确性 | 形式化保证 (类型+验证) | 概率性，可能生成错误代码 |
| 自修改安全性 | 四层防御 + 不可变内核 | 依赖 prompt engineering |
| 参数量 | ~38M | 7B-405B |
| 推理成本 | CPU 实时 | 需 GPU / API 费用 |
| 泛化能力 | 限于 ForgeLang DSL | 几乎所有编程语言 |
| 可解释性 | 修改即程序 diff，完全可读 | 黑箱权重变化 |
| 持续学习 | 原生支持 (知识库增量更新) | 需微调/RAG |
| 自然语言理解 | 弱 (SSM 仅做简单意图分类) | 强 |
| 生态工具链 | 几乎为零，需自建 | 极其丰富 |
| 研究价值 | 高 (探索新范式) | 低 (已有大量工作) |

**核心洞察**: NeuroForge 不是要取代 LLM，而是在 "可信自修改" 这个特定维度上做到 LLM 做不到的事。LLM 可以写代码，但不能证明自己写的代码是对的；NeuroForge 写得少，但写的每一行都有形式化背书。

## 8. 开放问题与风险

| 风险 | 缓解措施 |
|------|---------|
| ForgeLang 表达力不足 | 渐进扩展 DSL；允许 "unsafe escape hatch" 但需额外验证 |
| SSM 在小数据上过拟合 | 数据增强 + 正则化；Phase 1 先验证纯符号基线 |
| 自修改陷入局部最优 | 引入模拟退火式探索；定期重置搜索策略 |
| 沙箱逃逸 | nsjail 进程隔离 + 最小权限；定期审计沙箱实现 |
| 等价验证太慢 | 分层验证：快速 smoke test → 完整属性测试 → 符号证明 |
